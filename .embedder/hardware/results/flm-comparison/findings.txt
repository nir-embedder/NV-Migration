ProgramPage bounds / calls (shared-code.asm:284-505)
- 0x2e6 strips alias bit 28 for address classification. 0x2ee..0x2f2 requires 4-byte destination alignment on the ordinary flash path; 0x2f6..0x2fa rounds the byte count up to 4. It does not check source-pointer bounds/alignment, size overflow, destination+size wrap, or the 512 KiB/1 MiB device end.
- The ordinary flash branch is selected by normalized address <0x0f210000, not by a SKU-specific APROM end. 0x31c/0x35c/0x394 load source words/pairs and 0x31e/0x360/0x398 issue FMC command 0x61; 0x338/0x374/0x3b0 poll busy without an internal iteration timeout. The other controller branches classify additional address ranges, including a gated range ending 0x0f21e0ff; these are not KI/KJ APROM-limit checks.
- Normal valid page-buffer calls need not encounter these unchecked cases. A malformed length or buffer could fail, but saved artifacts do not establish that either occurred. Identical executable code cannot supply a KI-only MPU/interrupt/bounds implementation defect.

Conclusion
The SKU selection error changes host geometry and preservation risk, but no KI/KJ instruction difference explains the HardFault. Unchanged inherited stack limits and MPU state are credible hypotheses because the algorithm/standard call setup do not sanitize them and STKOF/IACCVIOL were observed. Unmasked interrupts or stale vectors after erase are another hypothesis, not an observed interrupt trace. Unknowns: actual MPU regions, stack-limit values/security bank, VTOR/NVIC/SysTick state, precise fault timing, stacked PC, and failing ProgramPage arguments. No saved evidence establishes a single root cause or validates a recovery sequence. No hardware retest or corrective firmware change was performed.
